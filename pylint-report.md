## 4. Design Decisions & Justifications

### 4.1 Database Service Signatures (`too-many-arguments`)
- Functions such as `create_device()`, `update_device()`, and `get_filtered_devices()` accept distinct parameters corresponding directly to SQLite table columns (`name`, `model`, `serial_number`, `description`, `type_id`, `category_id`, `location_id`, `os_id`, etc.).
- While Pylint flags functions with more than 5 parameters by default, keeping explicit parameter names ensures clear API contracts, accurate IDE autocompletion, and transparent data flow without hiding attributes inside opaque dictionaries. Targeted function-level suppressions (`pylint: disable=too-many-arguments,too-many-positional-arguments`) are applied exclusively to these data service functions.

### 4.2 DRY Query Organization
- Queries fetching device records with classification joins share a single canonical projection string (`DEVICE_SELECT_SQL`) defined in `devices.py`.
- `users.get_devices_by_user()` delegates directly to `devices.get_devices_by_user()`, eliminating duplicate SQL select lists across files and preventing Pylint `duplicate-code` notices while ensuring classification fields remain consistent everywhere in the application.

### 4.3 Security and Input Validation
- **SQL Injection Prevention**: Every SQL statement in the application strictly uses parameterized queries (`?` placeholders). No user-supplied values are interpolated into query strings.
- **CSRF Protection**: All state-changing `POST` requests are validated via `@app.before_request` against a cryptographic session token (`secrets.token_hex(16)`).
- **Authentication**: Passwords are never stored in plaintext; all credentials use salted hashes generated by `werkzeug.security.generate_password_hash`.
